# Baseline: what the current ETL costs to run and maintain (issue #525)

This gathers measurements and makes **no recommendation**. Later options (#529, #531, #532) are compared with these figures against the criteria agreed in #524. The status quo is gaiaDB with PL/sh and catalog entries generated by `etl()`.

```sh
benchmarks/baseline/measure_baseline.sh      # needs docker; writes the log shown in last_run.txt
```

**Run.** 13 November 2026 on an Apple Silicon Mac, with the `linux/amd64` image run under emulation (so the times are slower than a native Linux host; compare them with other runs on the same machine, not with absolute targets). Image `ohdsi/gaia-db@sha256:bd044e29...`; gaiaCatalog `dcb6d32`; gaiaDB working copy `a3c0ca3`. California only (`TRACT_STATES=06`). The line counts of gaiaDB are at commit `570a40b`, before the raster and point-source additions. One run, no repeats.

## The two cases

| | `mdc_hospitals` (a dataset) | `synthetic_road_proximity` (a derived dataset) |
|---|---|---|
| What it is | 37 hospital points from an ArcGIS REST service, 12 attributes | 62,401 distance-band polygons around the primary and secondary roads of California, built from `us_2019_prisecroads_tl` (7,403 lines) |

| ETL script lines | 201 | 47 (plus 61 for the roads) |

| Container start and initialisation | 10.9 s (once) | |

## Where the effort falls

**Steps from source to `EXTERNAL_EXPOSURE`:**
1. Author the entry: per the issue, a Box workbook and Kobo template feed the private `gdsc-tools` `etl()`, which writes the metadata and scripts. (Not run or checked here: it needs the Box key and the private repository.)
2. Commit the entry to gaiaCatalog.
3. Start gaiaDB with the catalog's `data` directory mounted at `/data`.
4. `backbone.ingest_datasource(table_id)`: load the JSON-LD (`metadata_load`), run `<table_id>_osgeo.sh` and then `<table_id>_postgis.sh` through PL/sh.
5. `backbone.gdsc_load_all_variables(...)`: build the `geom_`/`attr_` instance tables.
6. Load the locations (`working.load_location_data`).
7. `working.spatial_join_from_catalog(...)`: write `EXTERNAL_EXPOSURE`.

**gaiaDB code on that path:** five SQL files, 1,876 lines and 30 functions in all (`02` JSON-LD ingestion 477 lines, `03` locations 276, `04` spatial join 325, `05` retrieval 316, `06` catalog 482). Everything that runs a script goes through `gdsc_exec` (PL/sh).

**Findings from the two runs.**
- `mdc_hospitals` loads (37 rows in 2.1 s) but none of its 12 variables has a start or end date, so none is registered in `attr_index`. `gdsc_load_all_variables` then prints a warning and exits with success, so nothing signals the failure to a script, and step 7 cannot run. With the current metadata the dataset cannot produce an exposure row; the useful exposure from a hospital layer (distance to the nearest, count within) is a derived operation, the subject of #536.
- `synthetic_road_proximity` reaches `EXTERNAL_EXPOSURE`, but 455 s of the 474 s from the start of the roads ingest to the finished join are one SQL script (buffers and differences in 100 km tiles) written for this dataset. The script selects from the roads table, so the roads have to be ingested first; the entry states that dependency in its metadata, and as far as I can tell from `sql/05` `ingest_datasource` does not ingest dependencies for you (I did not try the entry without the roads).
- Each generated script exports the same six secrets whether the source needs any of them or not.

## Not measured here (needs people, access or other hosts)

- The authoring steps and their time: the Box workbook, the Kobo template and `etl()` (private). Someone should time adding one new dataset end to end, and record where a second person who has not done catalog work could not continue without help (this is the method in the issue; it is the main gap in this baseline).
- Timings on native Linux, Windows or macOS without emulation, and on a managed PostgreSQL service.
- Repeat runs, to give a range rather than one figure.
